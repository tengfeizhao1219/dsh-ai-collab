# AI 协作开发机制原理（MECHANISM）

> 本文件是 `ai-collab` 插件的机制说明：解释"为什么这套机制有效"，以及每个要素在整体中的位置。
> 改编自真实项目实践（"AI 情报官"多角色协作机制 v1.0，源自 One News 多会话协作框架），已剥离项目特定内容、通用化为任何软件项目可用。

---

## 0. 一句话

**文件即通信**：所有参与者（AI 角色 + 人类 owner）通过 git 仓库中的一组约定文件交换信息，不靠会议、不靠 IM、不催进度。任何新会话 / 新角色 / 新设备，读文件即可 100% 继承项目进度。

---

## 1. 机制设计原则

| 原则 | 含义 | 解决的问题 |
|---|---|---|
| **文件即通信** | 约定文件是唯一事实来源（Single Source of Truth） | AI 会话无持久记忆、跨会话/跨设备丢上下文 |
| **一个角色 = 一个固定身份** | 角色全程复用，身份由角色卡权威定义 | 多个 AI 会话/子 Agent 各自为政、互相覆盖 |
| **先读后动** | 新会话启动先按序读约定文件，再动手 | 新会话"失忆"，凭感觉干活 |
| **改前拉、改后推** | Git 纪律：pull --rebase 先行，一次逻辑单元一次提交 | 双端并行时文件冲突、进度丢失 |
| **小步快推** | 不堆积大量本地改动 | 交接时无法判断"改了哪些" |
| **显式留痕** | 每个交接点在 COMMLOG 倒序记录 | 进度靠问、靠翻对话，无法审计 |
| **关口检查** | 阶段级全 ✅ 才放行下一阶段 | 错误在阶段内累积，越到后面越难修 |
| **owner 只拍板** | 人类只在关键决策点决策、提供凭证；AI 显式请求，绝不编造 | AI 自作主张、编造资源/结论 |
| **AI 可消费产物** | 文档/代码/配置都结构化、术语一致、带交叉引用、可独立验证 | 文档写给人看，AI 读不懂、无法执行 |

## 2. 角色体系（O + 专业角色）

```
                 ┌─────────────┐
   人类 owner ──►│  O 主控       │  拆解任务、派发、关口检查、最终决策
                 │ (Orchestrator)│  持有全局上下文（一个会话/主代理）
                 └──────┬──────┘
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
  专业角色 A         专业角色 B       专业角色 C ...
  (子 Agent / 独立会话，临时扮演，身份从 ROLE_CARDS.md 获得)
```

- **O 主控**：全局持有者。在"100% AI + 子 Agent"模型中，O 是主会话/主代理；需要并行时派子 Agent 临时扮演专业角色。
- **专业角色**：各司其职。启动时读 `ROLE_CARDS.md` 对应角色卡获得永久身份（可以做什么 / 不可以做什么 / 产出目录 / 参与阶段 / 上级）。
- **身份一旦确定，该会话/子 Agent 就代表这个角色直至项目结束**——不许中途换角色，不许越权。
- 子 Agent 的"交付" = 写回约定文件（看板状态、COMMLOG 记录、产出物）。O 汇总后做关口检查。

## 3. 约定文件体系（核心五件套 + 导航）

| 文件 | 作用 | 维护者 | 读的时机 |
|---|---|---|---|
| `CONTEXT.md` | 项目速览：定位、硬前提、当前状态、技术速览 | 全员（会话结束时更新，谁改谁负责） | **第一必读** |
| `ROLE_CARDS.md` | 7（N）角色卡：身份/可以/不可以/产出目录/阶段/上级 | O | 子 Agent 启动时 |
| `TASK_BOARD.md` | 任务看板：任务级状态（认领/进行中/完成/阻塞） | 全员认领 | 认领前、交付后 |
| `RELAY.md` | 阶段流水线：当前阶段/里程碑/待拍板项 | O | 判断"当前该谁干活" |
| `COMMLOG.md` | 沟通交接记录：倒序，交接点留痕 | 全员 | 了解最新进展 |
| `COLLABORATION.md` | 协作总规：本机制的操作细则 | O | 所有角色 |
| `NAVIGATION.md` | 文档导航与交叉引用索引：AI 读者入口 | K | 拿到任意文档先读它 |

> **文档目录约定**：按阶段/领域分目录，避免互相覆盖（如 `docs/01-需求规划/`、`docs/02-产品设计/`、`docs/03-技术方案/`、`docs/04-开发实现/`、`docs/05-测试验收/`、`docs/06-上线复盘/`）。

## 4. 任务流转状态机

```
📋 待认领 ──认领(填角色)──► 🔄 进行中 ──完成(交付交接包)──► ✅ 完成
   ▲                            │                          │
   └──────────回退──────────────┴────阻塞────► 🚫 阻塞(+原因)
```

- **认领前核对归属**：看 `RELAY.md` 当前阶段是否属于自己 → 去 `TASK_BOARD.md` 认领。
- **交付交接包**（完成交接类任务必填）：做了什么 / 产出物清单 / 给下一棒的提醒。
- **3 分支意图识别**（收到指令时先判）：
  1. **主线**：「接棒/继续/该你」且 RELAY 显示当前阶段属于我 → 认领 🔴 任务。
  2. **误用棒**：说接棒但 RELAY 显示不是我 → ① 提示正确角色 ② 立即转即席（两步不可省）。
  3. **即席/直连**：对其他角色直接提诉求（问答、小改、临时需求）→ 权限内处理、轻量交付、不碰跟踪表；纯问答直接答。

---

## 5. 关口检查（Gate Check）

- 阶段级任务**全部 ✅** 后，由 O 做关口检查。
- 通过 → 开放下一阶段任务；不通过 → 回退并标记 🚫 + 阻塞项说明。
- 关口记录表：`关口 | 结果 | 检查人 | 日期 | 说明`（追加在 TASK_BOARD.md）。

> 关口是"阶段错误不后移"的关键防线：宁可阶段内返工，不让错误污染下游。

---

## 6. 阶段化流水线（RELAY）

```
Phase 0 环境与资源就绪 → Phase 1 … → Phase N 交付
```

- 每阶段记录：**目标 / 入口文档 / 状态 / 出口（下一棒输入）**。
- 阶段状态：⏸ 未开始 / 🔄 进行中 / ✅ 完成。
- **里程碑**：可验证的判定标准（如 M1 前端可预览 = demo + 页面落地）。
- **待 owner 拍板项**：集中列出，阻塞的标「阻塞-待 owner 提供」，继续推进不依赖项。

---

## 7. 并行最大化原则

- 无相互依赖的任务 → 派子 Agent **并行**（如多源适配器、多页面实现）。
- 有依赖 → 串行（基础设施先行）。
- 校验类工作（Q）可**全程并行**于其他工作。
- 并行时共同遵守 Git 纪律：改前拉、改后推、认领前看状态防双写冲突。

---

## 8. 会话继承（新会话如何无缝接棒）

**关键认知：AI 的"云端记忆"只带"你是谁"，文件机制才带"项目进行到哪"。**

新会话启动协议（`SESSION_BOOT.md`，复制即用）：
1. 按序读约定文件：CONTEXT → ROLE_CARDS → TASK_BOARD → COMMLOG → RELAY → COLLABORATION。
2. 向用户汇报**继承摘要**（≤300 字）：当前阶段 / 最近完成项（COMMLOG 最新 3 条）/ 当前待办（TASK_BOARD 进行中）/ 待 owner 拍板项（RELAY 末尾）。
3. 等待指令，按协作机制推进；改文件后立即 commit+push。

---

## 9. 同步通道（可选但推荐）

- **代码/文件 → Git**：守护进程每 60s 自动 commit+push（`scripts/git_sync.sh`），实时留档、多端一致。
- **文档 → Notion**：守护进程每 60s 幂等同步（`scripts/notion_sync.py`），未变更跳过。
- **凭证**：集中存于 secrets 文件（权限 600，不入库），新环境需重新配置。

---

## 10. 专业领域验收闭环（以 UI/UX 为例，可替换为任意专业域）

- **设计权威角色**（如 D 角色）：设计交付物标准 = ① 1:1 可交互原型 ② 精确规格文档 ③ 规范说明。
- **验收走查闭环**：设计权威角色做 UI/UX 验收，Bug 走提单格式。
- **不可自行推断**：其他角色 ❌ 不得自行改设计值（色值/间距/图标/状态覆盖）；遇技术限制先 @O 确认替代方案。
- **硬约束（如"零新增 hex"）**：写入 CONTEXT.md 的硬前提，Q 角色做红线审计。

---

## 11. 为什么这套机制能"用 AI 顺利完成项目"

1. **AI 会失忆，文件不会** → 机制把记忆外置到文件。
2. **AI 会并行，但会互相覆盖** → 角色卡 + 认领 + Git 纪律解决冲突。
3. **AI 会自作主张** → 角色"不可以"清单 + owner 拍板 + 硬前提红线约束。
4. **AI 会编造** → "AI 可消费产物标准" + 显式请求资源 + 交叉校验。
5. **项目会失控** → 关口检查 + 里程碑 + 阶段流水线。
6. **会话会换** → 继承协议 + 双通道同步，无缝接棒。

> 机制不依赖任何特定 AI 客户端（WorkBuddy / CodeBuddy / DeepSeek Harness / Claude 桌面端等均适用）——因为它的载体是**文件**。
